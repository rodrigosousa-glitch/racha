
CONTINUAÇÃO DO PROJETO — SISTEMA DE RACHAS DA EMPRESA
Quero que você continue comigo o desenvolvimento de um sistema web para organizar os jogos de futebol amador da empresa, chamados de rachas.
IMPORTANTE: não use "rachás". O correto neste projeto é:

singular: racha
plural: rachas
O sistema será usado principalmente pelo celular, mas também precisa funcionar bem em PC e tablet.
A prioridade é que seja extremamente simples de usar. A pessoa deve abrir um único link, encontrar o racha atual e conseguir participar rapidamente.

Análise técnica
O sistema é um app compartilhado de um único link, com um racha vivo, dinheiro, comprovantes privados e rankings. Não é uma página estática.

Três exigências puxam a arquitetura:

Segurança real — WhatsApp e comprovante não podem ir para o navegador de todo mundo. Esconder botão no celular não é segurança.
Barra imediata — quem anexa o comprovante precisa ver a meta subir na hora, sem recarregar.
Identidade simples — nome + WhatsApp, sem senha, e-mail ou SMS.
Sua ideia inicial (HTML + Supabase + GitHub Pages) funciona num projeto à parte. Aqui ela quebra em três pontos:

Ideia inicial	Problema	Decisão
GitHub Pages	Só serve arquivo estático. Sem servidor, o WhatsApp e o comprovante vazam no celular de qualquer um, e qualquer pessoa altera o racha pelo navegador.	Não usar. O app precisa de servidor.
Supabase + RLS	Boa ideia em tese. Neste app o Postgres já vem ligado na publicação, sem você criar conta, chave ou projeto extra.	Postgres no servidor, com as regras de permissão no servidor (equivalente ao RLS).
HTML + JS puro	Dá para fazer, mas rankings, upload, barra animada e tela ao vivo ficam mais frágeis.	App moderno (React), visual de aplicativo, pensado no celular.
O cliente nunca fala com o banco. O celular só chama o servidor. O servidor confere quem é você e só então lê ou grava. Isso atende o item 30 melhor do que RLS no frontend.

1. Arquitetura recomendada
Celular / PC
    │
    │  um único link
    ▼
App (telas + barra animada)
    │
    │  pedidos autenticados
    ▼
Servidor (todas as regras de negócio e permissão)
    │
    ├── Banco Postgres (jogadores, rachas, gols, dinheiro)
    └── Comprovantes (arquivo privado, só o organizador baixa)
Três camadas:

App — o que a pessoa vê. Atualiza a barra na hora (otimista) e depois confirma com o servidor.
Servidor — única porta para criar racha, participar, anexar comprovante, encerrar, finalizar, ver WhatsApp.
Banco — fonte da verdade. Dinheiro sempre em centavos inteiros, nunca em vírgula flutuante.
Não existe um link por racha. A tela inicial pergunta ao servidor: “tem racha ativo?” e mostra o atual ou o botão de criar.

2. Tecnologia recomendada
Camada	Escolha	Por quê
Telas	React + navegação por rotas	App de verdade, não site de 2005
Visual	CSS moderno, mobile-first	Celular primeiro, PC/tablet depois
Servidor	Funções no próprio app	Permissão de verdade, não botão escondido
Banco	Postgres	Dados duráveis, um racha ativo por restrição do banco
Arquivos	Comprovante no banco, privado	Sem serviço extra; só o organizador acessa
Identidade	Nome + WhatsApp + sessão no aparelho	Sem senha, sem e-mail, sem SMS
Tempo real	Atualização otimista + refresh curto	A barra sobe na hora para quem pagou; os outros veem em ~1–2 s
Por que não Supabase Realtime? O banco publicado aqui não tem canal ao vivo nativo. A sensação que você descreveu (“eu contribuí e vi a meta aumentar”) vem da atualização otimista: no instante do anexo, a barra já anima no seu celular. O servidor grava em seguida. Os outros aparelhos acompanham no ciclo curto. Isso é mais rápido para quem pagou do que esperar o push.

5–8. Modelo do banco
Dinheiro em centavos (integer). WhatsApp só dígitos. Um racha ativo imposto pelo banco, não só pela tela.

12. Fluxo de pagamento antecipado
Participar → entra como 🟡 Aguardando pagamento. Não conta na barra.

Excedente/déficit só calculados, nunca movimentados.
13. Fluxo de pagamento posterior
Participar → 🟢 Confirmado na hora. Barra sobe na hora.
Sem comprovante na entrada.
Tela mostra valor estimado, não definitivo.
Preço oficial = na finalização: campo ÷ quantidade de confirmados.
Quem confirmou e faltou continua devendo. Presença não tira a cobrança.
Exemplo: 12 confirmaram, 10 foram → 12 pagam.
14. Fluxo do furão
Furão só existe no pagamento antecipado:

Clicou participar.
Não enviou comprovante.
Organizador encerra inscrições.
🟡 Aguardando → 🐔 Furou. Continua no racha.
Se enviar comprovante depois: 🟢 Confirmado, furo daquele racha some.
Pagamento depois: participar já confirma. Falta no jogo é falta, não furada.

15. Fluxo de encerramento (e reabertura)
Encerrar inscrições ≠ finalizar racha.

Encerrar:

ninguém novo entra
racha continua ativo (não pode criar outro)
no pagamento antes, aguardando vira furão
organizador pode reabrir
Reabrir:

novas pessoas entram de novo
furões que já estavam: pergunta 2 (eu não decido)
16. Fluxo de finalização
Depois do jogo, o organizador finaliza:

trava inscrições (se ainda abertas — pergunta 3)
registra presença / falta
consolida gols
no pagamento depois, congela o preço oficial
calcula excedente ou déficit
atualiza rankings
libera a criação do próximo racha
Depois de finalizado, gols só o organizador altera.

17. Fluxo de gols e artilheiro
Cada jogador informa os próprios gols depois do jogo, antes de finalizar.
Organizador pode corrigir a qualquer momento daquele racha.
Depois de finalizado: só organizador.
Artilheiro = maior número de gols naquele racha.
Empate: todos os primeiros são artilheiros (dois 🥇).
Artilharia no perfil = quantas vezes a pessoa foi (co)artilheira em racha finalizado.

Furões: furadas, rachas, taxa. Exemplo 5 / 18 = 27,8% → o denominador inclui as furadas.

Perfil (vinculado ao WhatsApp, não ao nome):

gols, participações, furadas, artilharias, média

22. Excedente

Organizador: o mesmo + excedente ÷ confirmados como aproximado (R$ 5,88).

O sistema não devolve dinheiro e não tem botão “excedente resolvido”.

23. Déficit
10 × R$ 20 = R$ 200, campo R$ 240 → faltam R$ 40.

Participantes: aviso de que o arrecadado não cobre.

Organizador: déficit em destaque.

O sistema não decide como resolver.

No pagamento depois, déficit por confirmação demais não deveria existir: o preço é campo ÷ confirmados na finalização. Déficit típico é do pagamento antes (meta não atingida, preço já congelado).
